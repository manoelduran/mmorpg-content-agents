# SpriteKiln Art Briefs

*SPEC 1 of the Godot refactor PRD. Target: mmorpg-content-agents, plus a new
`mmorpg-art` workspace. mmorpg-backend and mmorpg-frontend are untouched.*

## Overview

The game's NPC and monster sprites are moving to SpriteKiln 0.4.0. SpriteKiln
renders 8-direction pixel art from a YAML spec that a coding AI writes and
refines. It is not an image model: a text brief is enough, and splash art is
optional. Art stops writing free-text prompts for a human to draw. It now
writes one structured **SpriteKiln brief** per entity, validated by zod like
every other agent output. A deterministic writer then turns each brief into a
**spec stub** (`spritekiln: 1`, `extends`, `use`, `brief`, and no geometry).
Rendering happens later, outside this pipeline: Claude Code models each stub
in the `mmorpg-art` workspace with SpriteKiln's own skill and MCP server.

Art keeps its shape: one schema-constrained OpenRouter call per entity, with
no tools. The AGENTS.md rule against tool-execution loops stays as it is. Art
also stops sending thumbnails of the current sprites. That old style is what
we are replacing. The art style now lives once, in the workspace's
`spritekiln.toml`, so Art no longer needs a vision-capable model.

Security review of SpriteKiln 0.4.0 (commit `17ae0ea`, 2026-11-24) found no
malicious code. The PyPI wheel is identical to the GitHub source, and the only
network access is an explicit `spritekiln update`. Keep the version pinned and
review again before any upgrade.

### Contracts

**`SpritekilnBriefSchema`** (domain). This is what the model returns. Brief
text is in English: it is internal production text read by SpriteKiln's
English-language agents, not player-facing, so `CONTENT_LANGUAGE_INSTRUCTION`
does not apply.

| field | type | rule |
|---|---|---|
| `entityId` | string | must equal the entity's id (extra validation) |
| `summary` | string | 1–2 sentences: what it is, silhouette, main colours |
| `base` | `"humanoid" \| "none"` | `humanoid` = SpriteKiln's built-in template; `none` = modeled from scratch (slimes, beasts) |
| `head` | string, optional | required when `base` is `humanoid` (extra validation) |
| `kits` | array of `SPRITEKILN_KITS`, unique, max 6 | must be empty when `base` is `none`, because kits attach to the humanoid skeleton |
| `mustKeep` | string[2..5] | traits that must read at sprite size; they become `review.keep` targets downstream |
| `simplify` | string[0..4] | details to drop at sprite size |
| `palette` | string[2..5] | colour/material words or hex (`"rusted iron"`, `"#7a3b2e"`) |
| `sizeClass` | `"small" \| "medium" \| "large" \| "huge"` | must be `large` or `huge` for an instance monster with role `BOSS` |

`SPRITEKILN_KITS` mirrors the built-in kits of SpriteKiln 0.4.0: `axe, belt,
bow, bun, cape, hair, hammer, hat, head, helmet, hood, mace, pistol, pouch,
ponytail, rifle, shield, spear, staff, sword`. Change it only when the pinned
version changes.

`requiredAnimations(kind)`: pure, decided in code and not by the model.
`npc` → `[idle, walk]`. `monster` → `[idle, walk, attack, hit, death]`.

**`AssetEntry`** (manifest, replaces the old shape):

```json
{
  "entityId": "rust-crawler",
  "kind": "monster",
  "relativePath": "assets/monsters/rust-crawler.png",
  "specPath": "art-specs/monsters/rust-crawler/rust-crawler.yaml",
  "source": "spritekiln-spec",
  "sourceDetail": "<brief.summary>",
  "transparent": false,
  "brief": { "...SpritekilnBrief minus entityId...": "" }
}
```

`relativePath` still says where the finished sprite will land. `transparent`
stays `false` until a rendered file exists. `sourceDetail` repeats
`brief.summary`, so any reader of the old field still gets one line. The old
`source` values are removed because nothing produces them any more. Manifests
already under `output/` no longer validate. This is acceptable: no installer
consumes them yet (AGENTS.md, "Manifests, not code").

**`IArtSpecWriter`**

```
write(cityId: string, assets: AssetEntry[], outputRoot: string): Promise<string[]>
```

Writes `<outputRoot>/<cityId>/<entry.specPath>` for every entry, atomically
(`writeFileAtomic`), and returns the paths it wrote.

**Stub format** (`renderSpritekilnStub`). Every scalar is written with
`JSON.stringify`. A JSON string is a valid YAML double-quoted scalar, so
names with `:` or quotes stay safe without adding a YAML dependency.

```yaml
spritekiln: 1
# Generated by mmorpg-content-agents for city "<cityId>". Model it with SpriteKiln 0.4.0.
name: "rust-crawler"
kind: character
extends: humanoid          # only when base is humanoid
use:                       # only when kits is non-empty
  - {kit: "sword"}
brief:
  summary: "..."
  head: "..."              # only when present
  must_keep: ["...", "..."]
  simplify: ["..."]
  palette: ["...", "..."]
  size: "medium"
  animations: ["idle", "walk", "attack", "hit", "death"]
```

SpriteKiln ignores everything under `brief:` (its schema is free text), so the
extra keys `palette`, `size` and `animations` are safe there.

### Business Rules

- Art makes exactly one model call per entity. It sends text only (no
  `image_url` parts), uses `ART_CONCURRENCY` as today, and keeps the resume
  semantics.
- Extra validation: wrong `entityId`; `humanoid` without `head`; `none` with
  kits; a BOSS whose `sizeClass` is not `large`/`huge`. Any of these goes back
  into the shared runner's corrective retry. No new retry machinery.
- Resume: an `alreadyCompleted` entry that fails `AssetEntrySchema.safeParse`
  (an old-shape checkpoint) is treated as pending and regenerated, not trusted.
- `specPath` and `relativePath` are derived in code from `kind` and
  `entityId`. The model never chooses a path.
- Stubs are written only by `execute()`, after `ValidatePackageUseCase`
  passes, and in the same step as the manifest. `executeDraft()` (`--skip-art`)
  never writes stubs.
- The system prompt states the 3/4 top-down, 8-direction, chibi-humanoid
  target and the kit list. It never mentions a human drawing the sprite.

## Art workspace (`/Users/manoelduran/Documents/test/mmorpg-art`, new repo)

```
mmorpg-art/
├── README.md            runbook: install, import a city, model, render, export
├── spritekiln.toml      written by init + the style interview (view, height, palette, outline...)
├── CLAUDE.md / .mcp.json / .claude/   written by `spritekiln init --ai claude` (SpriteKiln-owned blocks)
├── art/specs/<npcs|monsters>/<id>/<id>.yaml   stubs copied in from content-agents output (or written for the backfill), then modeled
├── art/specs/player/<layer>/<id>.yaml         player layers: body-<gender>, clothing-<style>, hat, kits (weapon-<archetype>, shield, cape)
└── (exports go straight into mmorpg-client/assets/spritekiln/<name>/ — engine=godot)
```

- Install: `pipx install "spritekiln[mcp]==0.4.0"`. Add `fast` only on Apple
  Silicon or Linux. No `splash` extra for now, because it downloads a
  background-removal model.
- `spritekiln init --engine godot --ai claude`, with the export root pointed at
  `/Users/manoelduran/Documents/test/mmorpg-client` (the Godot project now exists — F01–F12
  are done). `spritekiln render <spec> --export` writes `assets/spritekiln/<name>/`
  (`<name>.png` + `.json` atlas, `<name>.tres` SpriteFrames with one animation per
  `<anim>_<dir>`, `<name>.tscn` KilnSprite2D) and copies `addons/spritekiln/` into the
  client.
- Style (recorded once in the style interview): topdown 3/4 view, 8 directions, frame
  `size: 64` on the client's 32 px tiles at 1280×720 (characters overflow their tile, as the
  current art does), chibi humanoid proportions, one shared palette and outline.
- Run the style interview once, before the first asset. Its answers are the
  single art-style source that replaces Art's old thumbnails.
- Import is a plain copy of `output/<cityId>/art-specs/*` into `art/specs/`.
  No script yet: one city is about 26 files, copied once.
- `spritekiln init` must never run inside mmorpg-content-agents, because it
  rewrites marked blocks of CLAUDE.md/AGENTS.md there.

### Backfill of the sprites already in use
- The 22 distinct monster images and 14 NPC images the backend references today
  (`monsters.image`, `npcs.image`) are remodeled too. They get no Art brief, since these
  cities predate this pipeline; a stub is written by hand per image in
  `art/specs/<monsters|npcs>/<id>/`.
- The asset name is the current file name without `.png` (e.g. `merchant`), so the client
  maps `image` → `assets/spritekiln/<name>/` with no backend change.

### Player character (layers)
- SpriteKiln renders sheets; it doesn't compose a character at runtime. So the player is
  modeled as layers on one shared skeleton/height and rendered separately:
  - `body-male`, `body-female`;
  - `clothing-simple`, `clothing-tunic`, `clothing-armor`;
  - `hat`;
  - kits: `weapon-sword`, `weapon-bow`, `weapon-magic`, `shield`, `cape`.
- **Colour:** each layer marks its tintable regions through the palette, and the client tints
  hat and clothing at runtime from the F04 colours. Colours are never separate renders.
- **Animations:** `idle`, `walk`, `attack`, `hit`, `death`, all 8 directions. Every layer has
  the same frame count and timing.
- **Spike first:** render `body-male` + `clothing-tunic` + `hat` + `weapon-sword`, stack them
  in Godot, and check alignment frame by frame in all 8 directions for idle, walk and attack.
  Record the result here.
  - If it fails, the fallback is one sheet per gender × style (6 sheets) with runtime
    tinting, and no equipment on the body.

### Not SpriteKiln
- **Item icons** stay single-frame PNGs. The `prop` kind is animated and has no icon output.
- **Map tiles and objects** are a Godot TileSet (F15 of the PRD).

## Evals

- `evals/cases.py`: the `:art` case reads `assets[].brief` (with `entityId`)
  instead of `sourceDetail`. Rename `art_prompt_actionability` to
  `art_brief_actionability`, with steps for SpriteKiln briefs: silhouette and
  `mustKeep` legible at sprite size, a base and kits that fit the entity, a
  palette consistent with the city's atmosphere, no near-duplicate briefs
  across entities, and nothing impossible for a procedural 3/4 sprite (text,
  scenery, multiple characters). Same judge rules and threshold 0.7.

## Testing Strategy

- `spritekiln-brief.value-object.test.ts`: schema accept/reject with plain
  objects, plus `requiredAnimations`.
- `openrouter-art-agent.test.ts`: fake `ChatCompletionClient`. The request
  has no image parts; entries carry brief/specPath/source; each
  extra-validation rule triggers a corrective retry; old-shape resume entries
  are regenerated while new-shape ones are skipped.
- `spritekiln-stub.test.ts`: exact-string goldens for a humanoid with kits, a
  `none` base, and a summary containing `:` and `"`.
- `file-art-spec-writer.test.ts`: real temp dir. Files land at
  `<root>/<cityId>/art-specs/...`, and the returned paths match.
- `orchestrate-content-generation.use-case.test.ts`: in-memory fake writer.
  It is called once after validation in `execute`, never in `executeDraft`,
  and never when validation fails.
- Manual: `npm run typecheck`, `npm test`, `npm run build:schema`. Then one
  real `npm run generate` and the workspace round trip in plan.md.
